# Cooling beta-readiness review

27 October 2026 · Local review only. No live Render settings, GitHub branches, snapshots or deployment were changed. This is not a penetration test, dependency-vulnerability certification or proof of all chemistry.

## Decision

**Do not update the existing Render service yet.** The local cooling implementation is a plausible candidate for a small password-protected educational beta after the owner approves a release and the release checks below are completed. No new cooled chemistry is approved in this review. The eight current profiles apply to five of 24 reaction types; no blanket 24-type 3D support is asserted. Eight profiles and their actual scope are listed in [the Batch 4 audit](reaction-lab-cooling-batch4-final-audit.md), together with R8 restrictions and the complete 24-type inventory. R1/R2, R3 and Batch 2/3 reports were also reviewed; R3's full source was supplied, superseding older missing-source reminders.

### Release blockers / required before an update

1. **No frozen, reviewed candidate for the current local version exists yet.** The working tree contains uncommitted Batch 3 changes and untracked reports/tests; the local R3 checkpoint alone does not represent all current changes. Preserve these files and create a separately reviewed, immutable candidate only after publication is authorized. Include the runtime, required tests and reports deliberately, omit private files and screenshots unless explicitly authorized. Do not overwrite the earlier snapshots.
2. **Current hosted state was not inspected.** The local `render.yaml` sets manual deploy off, but cannot prove what Render currently has configured. The historical 20 October hosted record identified deployed commit `1f5a9a579e8d4bd7312932555060ccbbc926e480`, branch `codex/molecule-playground-beta-v1`, and Auto-Deploy Off; the local cached remote has that commit. Verify the actual branch, deploy, plan, HTTPS URL, secrets presence and Auto-Deploy Off in the dashboard before any release, without exposing secret values. Historical records and cached refs are not live verification.
3. **The new candidate has not been built in a container or hosted.** Local TypeScript/Vite build and synthetic gateway tests passed, but Docker/Podman were unavailable locally. A future approved candidate needs a clean Linux image build/import test and authenticated hosted smoke tests, including both named-profile workflows, 2D/3D, calculators, browser refresh, login/logout, mobile, health, cold start, memory and logs. A 320 px desktop Chromium viewport is not a physical mobile or Safari test.
4. **Prepare a rollback first.** Record the existing successful deployment and preserve the separate original and Expat-fixed local snapshots. Confirm the specific rollback option is available when needed; a rollback is not performed or assumed here. Do not switch or merge `main` as a substitute for a reviewed candidate.

## Security and deployment review

- `render.yaml` describes a Free Docker web service with `/healthz` and `autoDeployTrigger: "off"`. `Dockerfile` uses a pinned base, copies an allowlisted runtime, installs `libexpat1`, checks the real chemistry import, and runs as a non-root user. `.dockerignore` excludes environment files and key-like files; Git's ignore rules exclude common secrets and release archives. No tracked `.env` or `.pem`/`.key` paths were found. This was a **filename check**, not a full source/history secret scan.
- The production gateway requires a shared password and a random hexadecimal session key; missing/invalid configuration fails closed. The login and API require exact POST origin; the host is restricted. Signed, one-hour cookies are `Secure`, `HttpOnly`, `SameSite=None`, `Partitioned`, host-only, and responses are `private, no-store`. Authentication protects app pages and APIs; the minimal health endpoint is public. Open return redirects are limited to listed pages.
- This is a **shared-password beta**, not individual accounts or strong identity management. A copied valid cookie may remain usable until expiry; client-side logout is not global session revocation. Password or session-secret rotation affects shared access. Password length/secret format checks cannot prove a chosen password is secret or that a hex string was generated randomly. Do not paste either value into chat, URLs, source, screenshots or logs; privately verify independent, strong values in Render.
- Login/API throttles and the chemistry semaphore are process-local. The shipped one-worker configuration makes them coherent in that process, but workers/restarts reset counters and hosting proxies can group clients under a shared peer address. They are not distributed abuse protection. One sync worker and 512 MB Free capacity can cause queued requests, cold starts or a worker restart on long chemistry jobs; test real hosted load and retries before inviting more users.
- The login document has a restrictive CSP, but the main application response currently sets **frame-ancestors only**, not a complete script/source CSP. Treat that as defense-in-depth work for a later approved change; do not assume a comprehensive XSS security audit was performed. HTTPS and redirect enforcement depend on the hosting ingress; recheck there. PubChem searches/structures are sent to the external PubChem service; do not promise that molecule lookup terms remain solely on the device. Hosting/provider logs may also have their own retention policies.
- No live secret values, Render account data, actual current dashboard settings, public-repository history, package vulnerability database or third-party dependencies were inspected as part of this local review. No security claim should exceed those limits.

## Interface and chemistry confidence

The local rendered interface was inspected for each of the eight profiles at 1440 px and 320 px Chromium widths. All eight representative options matched, displayed a theoretical-conformer / not-temperature-simulation disclaimer and applicable condition notes; none caused document-level horizontal overflow or uncaught page errors in these checks. The five explicit source-reference profiles expose structured source observations, assumptions and unknowns in Guided Conditions when the inspector is opened. Perbenzoic acid has a guided explanation/reference but no equivalent structured fact panel; bromination and mCPBA have detailed condition notes but no Guided Conditions fact panel in the tested qualified views. Their backend descriptors exist, but a user should not be told all eight have the same visible provenance panel.

**Usability warnings:** condition messages are often long and use specialist terms such as “non-capturing,” “net model,” and “endpoint”; the important qualifier is present but may be hard for younger students to scan. The temperature help text names only the older Br2/mCPBA/perbenzoic examples, omitting the later explicit references. It says other **unvalidated** cases stay 2D, so it does not literally say all others are unsupported, but the examples are incomplete and could mislead discovery. Review concise copy, discoverability and provenance presentation before or shortly after a small beta; no UI change was made here. On mobile, open **Edit conditions** to see the inspector and Guided Conditions.

Representative cooled chlorination, SN2 and primary alcohol oxidation were checked at desktop/mobile: conditional 2D and explanatory limitations were shown, 3D was disabled, and the messages did not assert chemical impossibility. They are detailed but verbose. Other unsupported types are covered by the existing 25-case backend cooling matrix, not individually re-inspected in a browser in this review. A source search did not find a claim in the app that all 24 pathways support cooled 3D. Existing benchmark case A304's incorrect-result flag is an independently documented frozen expectation defect, not evidence that this review has discovered a new production defect; keep its classification and the benchmark unchanged.

## Profile-switch race and other verification

The previously missing test is now reproducible in [the local browser test](../tests/cooling-beta-profile-switch.browser.cjs). At both 1440 px and 320 px, it held a valid isobutylene/HCl 3D response, changed the reagent, explicitly confirmed the valid isobutylene/Os/H2O2 source profile, then released the old response. The old result, measurements and calculator output stayed cleared; the new profile produced the expected theoretical glycol. This is a specific cross-pathway transition that changes both reagent and profile, not a proof of every possible transition or scheduling interleaving. The test uses a temporary localhost QA server, not Render's production ingress.

- Focused production gateway, Render packaging and eight-profile/R8 checks: **42 Python tests passed**.
- Cooling matrix, Batch 2 boundary and R3 checks: **78 Python tests passed**.
- Frontend condition/profile guidance and registry checks: **47 JavaScript tests passed**.
- The unchanged 347-case audit was rerun and every per-case result matched the stored R3 baseline: 155 fully supported, 90 unsupported, 38 correctly rejected, 63 partially supported and one known frozen incorrect-result flag.
- TypeScript and local production frontend build passed. Existing Vite large-chunk and third-party directive warnings remain.
- The full 4,364-test suite was last run in Batch 4; it was **not rerun** for this review. Focused results above do not replace a final full regression run for the future release candidate.
- The temporary local test server was stopped. `git diff --check` passed for tracked files; the current worktree remains intentionally dirty with prior user work and this report/test. UI/UX Pro Max informed the focused review of feedback clarity and responsive overflow, not a redesign.

## Recommended checklist after explicit approval

1. Review and freeze the exact candidate from the local working tree on a separate release branch/snapshot; verify untracked additions, secrets exclusion, intended public-repository visibility and file hashes. Preserve existing branches, snapshots and staged/user changes; do not push or merge without the relevant approval.
2. Run the complete Python and JavaScript regression suite, focused browser tests, TypeScript/build, unchanged 347-case audit, dependency/security review and clean container build against that frozen candidate.
3. Record the current Render deployment, service plan, settings and rollback option. Confirm Auto-Deploy remains Off; separately verify correct HTTPS origin and securely configured independent password/session key without disclosing them.
4. Only with explicit deployment approval, use a separate staging service or a deliberate manual deployment of the chosen immutable commit, preserving a verified rollback. Never silently update the frozen v1 branch or `main`.
5. Test the actual hosted build and public-facing authentication with the owner, 2D/3D and condition-blocking flows, profile-switch race, mechanisms/calculators, cold restart and real browser/mobile behavior. Check logs for secret leakage and service limitations.
6. Share privately only after those checks pass; label outputs theoretical and collect reproducible bug reports. Stop and remediate any blocking regression rather than silently broadening a chemistry rule or changing the budget/plan.
